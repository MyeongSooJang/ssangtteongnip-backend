# PR 양식과 머지 절차

PR을 만들거나 머지할 때만 읽는다. 커밋·브랜치 규칙은 `SKILL.md`에 있다.

## PR 양식

### 제목
커밋과 같은 형식 `type(scope): 한국어 설명`을 쓴다. merge commit으로 머지하면 이 제목이 main의 머지 커밋 메시지에 남아 PR 단위를 구분하는 기준이 된다.

### 본문
아래 섹션을 순서대로 포함한다. 해당 없는 섹션은 "해당 없음"으로 적거나 생략한다.

```markdown
## 관련 이슈
<!-- Closes #번호. 없으면 생략 -->

## 변경 사항
<!-- 무엇이 바뀌었는지 bullet으로 -->

## 변경 이유
<!-- 왜 이 변경이 필요했는지, 어떤 문제를 해결하는지 -->

## 리뷰 포인트
<!-- 리뷰어가 집중해서 봐야 할 부분, 고민했던 설계 결정 -->

## 테스트 계획
- [x] 자동화 테스트: (실행한 테스트와 결과)
- [x] 직접 실행 확인: (서버·화면·API를 직접 띄워 확인한 내용. 해당 없으면 줄을 삭제)

## 배포 영향
<!-- DB 마이그레이션, 환경변수 추가, 롤백 방법 등. 없으면 "없음" -->

## 스크린샷
<!-- UI/API 응답 변경 시. 없으면 생략 -->

## 체크리스트
- [ ] Breaking Change 없음 (있다면 위 변경 사항에 설명)
```

### 작성 규칙
- 본문에 `🤖 Generated with Claude Code` 등 AI 서명을 넣지 않는다.
- "코드 리뷰 후속 작업" 체크리스트 섹션을 넣지 않는다.
- 테스트 결과는 실제로 실행한 것만 체크한다. 실행하지 않은 항목을 체크하지 않는다.
- "수동 확인" 체크박스처럼 사람이 나중에 확인할 항목을 PR에 남기지 않는다. 서버·화면·API는 PR을 만들기 전에 직접 실행해 확인하고, 확인한 결과만 "직접 실행 확인"에 적는다. 확인하지 못한 것은 체크박스로 두지 말고 리뷰 포인트에 "미확인: 이유" 문장으로 적는다.

### 머지 전 확인
사용자가 머지를 지시하거나 확인했고 아래 항목이 모두 충족되면 `gh pr merge --merge --delete-branch`로 머지하고, 머지 후 `main`을 최신으로 갱신(`git switch main && git pull`)한다.

1. PR이 `main` 대상이고 충돌이 없는가 (`mergeable`)
2. 테스트 계획의 항목이 실제로 실행되어 통과했는가 (이번 세션에서 실행한 결과 기준)
3. CI 체크가 설정되어 있다면 통과했는가
4. team 모드: 리뷰어 승인(`reviewDecision`이 `APPROVED`)이 있는가
